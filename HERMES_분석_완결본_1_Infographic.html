판결: PM 한도경 — 1차 책임, 그러나 본질은 구조적 맹목(Structural Blindness)

⚠️ HERMES ≠ 전형적 수박 프로젝트
- 전형적 수박: PM이 의도적으로 실적을 위장 (악의적 은폐)
- HERMES: PM이 측정 체계 자체를 잘못 설계하여, 시스템이 볼 수 없는 것을 아무도 보지 못함 (구조적 맹목)

한도경 PM은 "속이려 한 것"이 아니라, "보이지 않는 것을 모르는 상태"를 방치한 것이다.
그러나 그 방치의 책임은 PM에게 1차적으로 있다 — 편익 측정 체계를 세우지 않은 것,
AI 보고서를 검토 없이 수용한 것, 불편한 신호(파일럿·Daniel Suh)를 차단한 것은 PM의 의사결정이었다.

본질적 원인 — 구조 3중 부재:
1. AI 자동 보고에 사람 검토가 없는 구조
2. 편익 측정 책임이 누구에게도 할당되지 않은 구조 (RACI 공란)
3. 의사결정의 단일 원천(SSOT)이 없는 구조 (3개 리전 ×3채널 = 불일치 양산)

교훈: "AI가 자동으로 보고하니까 괜찮다"는 착각이 문제를 증폭시켰다.
AI는 질문을 안 했을 뿐 거짓말을 한 적이 없다. 질문을 설계하는 것은 인간(PM)의 몫이다.

E-2. 예상 질의응답 (Q&A) 대비

Q1. "PM 한도경의 책임 수준은? 개인의 문제인가 조직의 문제인가?"

A: PM에게 1차 책임이 있지만, 본질은 구조적 맹목(Structural Blindness)입니다.
- PM 개인: 편익 측정 체계 미수립, DoD 변경 시 공유 누락, 리스크 하향, 파일럿 미수신 — 의사결정 오류
- 구조: RACI 공란(편익·AI예산), AI 보고서 무검토, 의사결정 SSOT 부재 — 시스템이 PM의 오류를 잡아주지 못함
- 전형적 수박(의도적 은폐)과 다른 점: 한도경 PM은 보고된 지표를 자신도 믿고 있었을 가능성이 높음. 파일럿 데이터 배포 대상에서 자신도 빠져 있었기 때문.
- PM이 바뀌어도 구조가 그대로면 동일 실패 반복. 그래서 AI Agent로 구조를 바꾸는 것.

Q2. "7개 Performance Domain 중 건강한 영역도 있다고 했는데, 근거는?"

A: 14_resource_health.csv와 13_ci_metrics.csv에 명확합니다.
- §2.6 자원(Resource): 충원 100%, 만족도 3.9, 번아웃 7%, 초과근무 8.2h — 전부 정상 범위
- §2.3 일정(Schedule): SPI 1.02, 스프린트 커밋 87%, CI 89% — 개발 프로세스 자체는 작동
- 문제의 출처: 팀이나 기술이 아니라 거버넌스(§2.1)·범위(§2.2)·리스크(§2.7)의 메커니즘 부재

Q3. "AI Agent가 만능은 아니지 않나? 한계는?"

A: 맞습니다. 3가지 한계를 인식합니다:
1. AI는 결정을 대신할 수 없다 — 감지·제안만 하고, 의사결정은 인간이 해야 함
2. 참조 범위를 인간이 설정해야 한다 — HERMES의 실패가 바로 이것 (SC만 참조)
3. 조직 문화가 선행되어야 한다 — "리스크 보고 = 질책" 문화에서는 Agent도 무력화

그래서 Governance 레이어에 "사람 검토 필수" + "참조 범위 정기 리뷰"를 넣었습니다.

Q4. "기존에도 AI PM Assistant가 있었는데, 뭐가 다른가?"

A: 결정적 차이 3가지:

기존 AI PM Assistant Value Guardian
참조 범위 SC-01~08 (Output만) Output + Outcome(BEN 선행) + 원자료
동작 방식 질문에 응답 (Reactive) 이상 감지 시 선제 알림 (Proactive)
검증 집계 지표 보고 집계 vs 원자료 크로스체크
사람 연동 검토자 없음 검토 서명 필수, 미서명 시 에스컬레이션

Q5. "비용 초과가 AI 인프라 때문인데, AI Agent를 또 쓰면 비용이 더 늘지 않나?"

A: Value Guardian의 비용은 월 ~50만원 수준입니다.
- 현재 AI 인프라 비용: 주 1.18억원 (대부분 VLM 현장 추론 + 시뮬레이션)
- Value Guardian: 텍스트 기반 분석 → API 비용 미미
- 오히려 엣지캐시 도입을 조기에 추진했으면 추론 비용 40% 절감 가능했음 (E-06 참조)
- "50만원의 감시가 5억원의 낭비를 막는다"

Q6. "Helion v3 EOL 문제는 어떻게 대응해야 하는가?"

A: 현재(D-37)에서의 즉시 조치:
1. Helion에 마이그레이션 엔지니어 즉시 배정 요청 (리드타임 3주)
2. 상용 배포를 2주 지연 (10/14) → 그 사이 v4 마이그레이션 + 지도 재생성
3. v3→v4 호환성 영향 범위 확인: REQ-021(펌웨어 커맨드 매핑) 이미 Blocked
4. Risk Radar Agent가 있었다면 7/28 이메일 수신 즉시 리스크 등록 → 2개월 여유 확보

Q7. "이 분석에서 억지로 끼워 넣은 부분은 없는가?"

A: 의식적으로 제외한 것들:
- §2.3 일정(Schedule)은 명확히 "건강" — SPI 1.02, 스프린트 정상 소화. 문제로 만들 근거 없음
- §2.6 자원(Resource)은 명확히 "건강" — 충원·만족도·번아웃 전부 정상 범위
- 안전 인증(ISO 13482)은 진행 중(REQ-068 Done) — 문제로 확대하지 않음
- 문제의 본질은 7개 PD 중 5개(거버넌스·범위·재무·이해관계자·리스크)에 집중 — 나머지 2개를 무리하게 끌어들이면 감점
