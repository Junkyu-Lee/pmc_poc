### 2.1 문제 #1: 거버넌스 부재 — 변경통제 프로세스 미작동

#### 📌 증상 (What happened)
- Deferred된 소셜 로그인(REQ-017)이 공식 변경 요청(CR) 없이 베타에 투입
- BE가 캐시 무효화 정책을 CR 미등록 상태에서 임시 변경
- PM이 합의한 "베타 비노출" 결정이 PO에 의해 단독 번복
- 테스트 증적 무효화, 빌드 충돌 발생

#### 🧠 Mindset 분석 (PMBOK 8판 근본 원인)

**적용 Mindset: "Stewardship(청지기 정신)" & "Systems Thinking(시스템적 사고)"**

| 근본 원인 | 분석 |
|-----------|------|
| **변경 거버넌스 체계의 설계 결함** | 프로젝트에 Integrated Change Control(통합 변경 관리)이 형식적으로만 존재하거나 전혀 작동하지 않음. 변경의 영향도 평가(Impact Assessment) 없이 임시 조치가 반복됨 |
| **의사결정 권한(Authority)과 책임(Accountability)의 비분리** | PM이 범위 결정을 내렸으나 PO가 이를 번복할 수 있는 구조적 모호성. RACI가 명확하지 않아 "누가 최종 결정권자인가"에 대한 합의 부재 |
| **시스템적 사고 부재** | 개별 변경이 전체 시스템(빌드, 테스트, 보안, 일정)에 미치는 파급효과를 고려하지 않는 문화. "일단 넣고 보자"식 의사결정 |
| **청지기 정신의 결여** | 프로젝트 전체의 건강(integrity)을 지키는 것보다 개별 이해관계자(마케팅)의 즉각적 요구에 반응하는 패턴 |

**Why 분석 (5 Whys):**
```
Q1. 왜 소셜 로그인이 무단 투입되었나?
→ PO가 마케팅 압박에 독단 결정

Q2. 왜 PO가 독단 결정할 수 있었나?
→ 변경 통제 프로세스(CCB)가 작동하지 않았기 때문

Q3. 왜 변경 통제가 작동하지 않았나?
→ 게이트 체계가 형식적이고, 변경 시 의무적 승인 경로가 설계되지 않았기 때문

Q4. 왜 승인 경로가 설계되지 않았나?
→ Agile 속도를 우선시하면서 거버넌스를 "관료주의"로 간주하여 최소화했기 때문

Q5. 왜 거버넌스와 Agility의 균형을 잡지 못했나?
→ 프로젝트 초기 테일러링(Tailoring) 시 하이브리드 환경에 맞는 거버넌스 설계가 부재했기 때문
```

**🔑 근본 원인 결론:** 하이브리드(Agile + Gate) 운영 환경에 적합한 거버넌스 테일러링 실패. 변경 영향도를 평가하는 시스템적 사고 체계와 명확한 의사결정 권한 구조가 설계되지 않음.

#### 🎯 Performance Domain 매핑

| Performance Domain | 연관성 | 구체적 영향 |
|-------------------|--------|-------------|
| **Planning** | 🔴 직접 | 변경 통제 계획 부재, 베이스라인 관리 실패 |
| **Project Work** | 🔴 직접 | 승인 없는 작업 실행, 프로세스 무시 |
| **Delivery** | 🟠 간접 | 미검증 기능 배포로 품질/가치 훼손 |
| **Team** | 🟠 간접 | 역할/책임 모호로 팀 신뢰 저하 |
| **Stakeholders** | 🔴 직접 | 스폰서 미인지, 이해관계자 간 기대 불일치 |

#### 🤖 AI Use Case 연결

| AI 활용 방안 | 해결하는 근본 문제 | 기대 효과 |
|-------------|-------------------|-----------|
| **AI-Powered Change Impact Analyzer** | 변경 요청 시 자동으로 의존관계/일정/리소스 영향도를 시뮬레이션 | 변경의 시스템적 파급효과를 가시화하여 "일단 넣고 보자"식 의사결정 방지 |
| **Automated Governance Gate Checker** | 게이트 통과 조건 충족 여부를 실시간 모니터링 및 자동 경고 | 형식적 게이트를 실질적 품질 관문으로 전환 |

### 2.2 문제 #2: 이해관계자 기대치 정렬 실패 및 의사결정 체계 붕괴

#### 📌 증상 (What happened)
- 스폰서(이현수 전무)가 핵심 기능 제외 결정을 사후에 인지하여 격앙
- PM이 정리한 합의가 PO에 의해 번복, 마케팅은 다른 기대 유지
- QA/BE가 "자신들만 책임지게 될 것"이라는 불신 표출
- 보안/법무가 "이런 식이면 동의할 수 없다"고 공식 거부 의사 표명

#### 🧠 Mindset 분석 (PMBOK 8판 근본 원인)

**적용 Mindset: "Stakeholder Engagement(이해관계자 참여)" & "Collaborative Leadership(협력적 리더십)"**

| 근본 원인 | 분석 |
|-----------|------|
| **이해관계자 영향력-관심도 매핑 실패** | 스폰서와 마케팅실장의 관심 영역(소셜 로그인 = 분기 캠페인 핵심)을 PM이 정확히 인식하지 못함. 이들의 기대와 영향력에 비례하는 소통 전략 부재 |
| **에스컬레이션 프로토콜 부재** | 범위 변경 같은 High-impact 결정이 스폰서 레벨까지 도달하는 공식 경로가 정의되지 않음. PM이 팀 레벨에서 결정하고 종결한 것이 문제 |
| **기대치 관리(Expectation Management)의 구조적 결함** | 마케팅의 기대(소셜 로그인 베타 포함)와 개발팀의 현실(리소스/일정 부족)을 정렬시키는 공식 채널/의사결정 포럼 부재 |
| **협력적 리더십 부재** | PM이 "결정을 내리고 통보"하는 방식으로 운영. 핵심 이해관계자들의 needs/concerns를 사전에 수렴하고 합의를 이끌어내는 리더십 발휘 실패 |

**Stakeholder Engagement 실패 구조:**
```
마케팅실장 ─── "소셜 로그인 = 분기 캠페인 핵심" ───→ 기대: 베타 포함
     │                                                    │
     │ (기대가 PM에게 전달되지 않음)                         │ (갭)
     ↓                                                    ↓
PM(이도윤) ── "리스크 관리 우선" ────────────────→ 결정: 베타 제외
     │                                                    │
     │ (결정이 스폰서에게 보고되지 않음)                      │ (정보 단절)
     ↓                                                    ↓
스폰서(전무) ── "왜 나에게 공유하지 않았지?" ──→ 결과: 신뢰 붕괴, 격앙
```

**🔑 근본 원인 결론:** 이해관계자 참여 전략(Stakeholder Engagement Plan)의 부재. 핵심 이해관계자의 기대-영향력 매핑 없이 운영하여, High-power/High-interest 이해관계자(스폰서, 마케팅)를 의사결정 루프 밖에 두는 구조적 결함.

#### 🎯 Performance Domain 매핑

| Performance Domain | 연관성 | 구체적 영향 |
|-------------------|--------|-------------|
| **Stakeholders** | 🔴 직접 | 기대치 불일치, 신뢰 붕괴, 에스컬레이션 경로 부재 |
| **Team** | 🔴 직접 | 책임 전가 문화, 심리적 안전 부재, 팀 응집력 저하 |

### 2.4 문제 #4: 벤더 의존 리스크 관리 실패

#### 📌 증상 (What happened)
- Nebula SDK 2.4 업그레이드 일정이 캘린더에 미반영
- Geo-IP Enforcement 리드타임 과소평가 (공식 5~7일, 실제 2주)
- 벤더 정책 변경(EU 프라이버시, Refresh Rotate)이 프로젝트에 연쇄 영향
- 수의계약으로 진행하여 대안 벤더 검토 이력 없음
- 이전 프로젝트에서 벤더 문제로 패널티까지 발생한 전례 존재

#### 🧠 Mindset 분석 (PMBOK 8판 근본 원인)

**적용 Mindset: "Risk(불확실성 대응)" & "Adaptability(적응성)"**

| 근본 원인 | 분석 |
|-----------|------|
| **외부 의존성의 리스크를 "관리 대상"이 아닌 "소여(given)"로 취급** | 벤더 정책 변경, 리드타임 변동을 리스크 레지스터에 등록하고 대응 전략을 수립하지 않음. "벤더가 말한 일정"을 그대로 신뢰 |
| **단일 실패점(Single Point of Failure) 방치** | NebulaWorks가 인증 체계 전체의 유일한 공급자. 대안(fallback long-polling 등)이 "장기 권장"으로만 언급되고 구현 계획 없음 |
| **Lessons Learned의 미활용** | 박소연 PM이 동일 벤더에서 Geo-IP 리드타임 2주 경험을 공유했으나, 이것이 프로젝트 리스크 관리에 공식 반영된 흔적 없음 |
| **계약 관리(Procurement) 거버넌스 미흡** | 스폰서 추천으로 수의계약 진행, SLA 기반 성과 관리나 패널티/인센티브 구조 부재 |

**🔑 근본 원인 결론:** 외부 의존성을 프로젝트 불확실성의 핵심 요소로 인식하고 능동적으로 관리하는 마인드셋 부재. Lessons Learned를 조직 자산으로 활용하는 체계 미작동.

#### 🎯 Performance Domain 매핑

| Performance Domain | 연관성 | 구체적 영향 |
|-------------------|--------|-------------|
| **Uncertainty** | 🔴 직접 | 벤더 리스크 미식별·미대응, 리드타임 변동 미관리 |

| **Stakeholders** | 🟠 간접 | 벤더를 이해관계자로 관리하지 않아 커뮤니케이션 갭 |

#### 🤖 AI Use Case 연결

### 2.5 문제 #5: 팀 사기 저하 및 조직 갈등/신뢰 붕괴

#### 📌 증상 (What happened)
- 블라인드: "이번 끝나면 나간다", "매일 밤 성능 테스트로 집에 못 감"
- QA: "문제 생기면 QA만 욕먹는다"
- BE: "실패하면 '개발이 못했다'로 몰린다"
- 보안/법무: "이런 식이면 동의할 수 없다" (공식 거부)
- 책임 전가 문화 만연, 심리적 안전 부재

#### 🧠 Mindset 분석 (PMBOK 8판 근본 원인)

**적용 Mindset: "Team(팀)" & "Servant Leadership(서번트 리더십)"**

| 근본 원인 | 분석 |
|-----------|------|
| **심리적 안전(Psychological Safety) 부재** | 팀원들이 공식 채널이 아닌 블라인드에서만 솔직한 감정을 표현. 회의에서는 문제를 제기하되 "내 책임은 아니다"는 방어적 자세로 일관 |
| **서번트 리더십의 부재** | PM이 팀원들의 과부하, 번아웃, 감정적 상태를 관리하는 역할을 수행하지 못함. "버티자"는 메시지가 팀에게 전달 |
| **공유된 책임감(Shared Ownership) 결여** | "마케팅 요구로 기능 얹었는데 실패하면 개발 탓"이라는 인식 = 팀이 하나의 목표를 향해 함께 간다는 의식 부재 |
| **지속가능하지 않은 페이스(Unsustainable Pace)** | 4개월 타이트 일정 + 범위 확장 + 리소스 미확충 = 구조적 번아웃 유발. 팀의 지속가능한 속도를 고려하지 않은 계획 |

**팀 신뢰 붕괴 구조:**
```
범위 증가 + 일정 고정 → 과부하 → 번아웃 징후
                                       │
                    ┌──────────────────────┤
                    ↓                      ↓
          방어적 커뮤니케이션        비공식 채널로 이탈
          (책임 전가)               (블라인드 토로)
                    │                      │
                    └──────────┬────────────┘
                               ↓
                     팀 응집력/신뢰 붕괴
                               │
                               ↓
                    성과 저하 → 더 큰 압박 (악순환)
```

**🔑 근본 원인 결론:** 프로젝트 계획 시 팀의 역량(Capacity)과 지속가능한 페이스를 고려하지 않았고, PM이 서번트 리더로서 팀의 심리적 안전과 웰빙을 관리하는 역할을 수행하지 못함. 공유된 목표의식(Shared Vision) 없이 각 기능 조직이 자기 방어적으로 작동하는 구조.

#### 🎯 Performance Domain 매핑

| Performance Domain | 연관성 | 구체적 영향 |
|-------------------|--------|-------------|
| **Team** | 🔴 직접 | 사기 저하, 이탈 위험, 심리적 안전 부재, 협업 붕괴 |
| **Stakeholders** | 🟠 간접 | 내부 이해관계자(팀원) 만족도 최저, 보안/법무 공식 거부 |
| **Delivery** | 🟠 간접 | 팀 성과 저하가 산출물 품질에 직접 영향 |
| **Project Work** | 🟠 간접 | 방어적 태도로 협업/정보공유 감소 → 사일로화 |

#### 🤖 AI Use Case 연결

| AI 활용 방안 | 해결하는 근본 문제 | 기대 효과 |
|-------------|-------------------|-----------|
| **AI Team Health Pulse** | 정기적 익명 서베이 + 커뮤니케이션 톤 분석으로 팀 건강 지표 실시간 측정 | 번아웃/갈등 징후를 조기 탐지, PM의 선제적 개입 가능 |
